# 自托管部署与运营交接

本项目是可自托管、多账号的单进程产品，公网域名现统一为 `https://prispect.com`。新域的 DNS、证书、Origin、认证与部署验收须单独记录；实际部署、本机检查与尚未执行的 Docker、容量验证分别记录。

## 本机运行

使用 Node 22.12 或以上版本。`npm ci` 需要执行 better-sqlite3 的原生依赖安装脚本，不能加 `--ignore-scripts`。初次启动前执行 `npm run build`，然后 `npm start`，同源入口为 `http://127.0.0.1:4317`。开发使用 `npm run dev`，网页端口为 4318。

`.env.example` 不含密码或模型凭据。复制为 `.env` 后按本项目授权填写。默认只监听本机；工作区、账号数据库、会话与智能体检查点都在 `CASHLENS_DATA_DIR` 下，必须保留这一目录。认证采用 Better Auth；生产必须配置独立、持久的 `BETTER_AUTH_SECRET`（至少 32 字符），不能每次发布重新生成。

## 单台服务器

1. 使用专用部署目录、非 root 用户和当前安全维护的 Node 22；拉取私有源码需要团队授权。
2. 执行 `npm ci`、`npm run check`。配置 `NODE_ENV=production`、`HOST=127.0.0.1`、`PORT=4317`、`APP_ORIGIN=https://prispect.com` 与独立持久化数据目录。
3. 用服务管理器运行 `npm start`，由 HTTPS 反向代理同源转发。核对 `deploy/Caddyfile.example` 中主域与 www 的配置；DNS 与证书需要真实部署环境。
4. 确认账号注册、登录、退出、改密、两个账号之间的材料/任务隔离以及导出。检查安全 Cookie 仅通过 HTTPS 发送，直接跨域写入被拒绝。
5. 配置进程监控、`/api/health` 探测、磁盘容量告警与备份。不要记录密码、Cookie、模型密钥或上传材料全文。

原生部署模板为 `deploy/cashlens.service`，假定 Node 位于 `/usr/local/bin/node`、源码入口 `/opt/cashlens/current`、状态 `/var/lib/cashlens`；实际部署会验证这些路径。`cashlens-backup.timer` 每日北京时间 04:30 运行一致性备份，短暂停止本服务以完整保存 SQLite 和用户工作区，同时将 `/etc/cashlens.env` 保存为备份中的 `configuration/cashlens.env`，之后自动启动。备份包含密钥，仅 root 可读取；不删除旧备份，运营方根据磁盘监控确认保留策略。

`cashlens-health.timer` 每五分钟运行本机健康接口与磁盘检查。启动阶段的短暂连接失败允许重试；数据盘使用率达到 85% 或接口持续失败时，该次服务失败并在 journal 留下记录。当前没有外部通知或自动清理旧备份。

不把客户端转发头自动当可信身份。应用端口保持本机绑定；反向代理的 IP 信任规则只能针对已确认代理配置。公网入口与 HTTPS 的实际验证由部署验收记录说明。

## 容器路径

提供 `Dockerfile` 和 `compose.yml`。执行时必须指定真实 `APP_ORIGIN`：

```bash
APP_ORIGIN=https://cashlens.your-domain.example docker compose up --build -d
```

容器以非 root 用户运行，宿主端口只暴露在 127.0.0.1；同样需要 HTTPS 反向代理。命名卷 `cashlens-state` 保存账号与工作区，不能在清理时删除。示例域名不会提供真实入口。本环境是否具有 Docker 以及该链路是否实测，应以验收文档为准。

原始年报不烘焙进镜像。事实样本和外部出处仍可使用；如需本机原件定位，先运行 `npm run data:fetch` 校验并下载，再仅在有权限的部署范围内只读挂载 `data/raw/`。商业再分发须先确认许可。

## 数据备份和恢复

初期单进程部署采用最简单可验证路径：停止服务并等待正在处理的任务结束，然后完整备份 `CASHLENS_DATA_DIR`；同时备份部署配置，密钥另以安全方式保存。只复制某个 JSON 文件不能备份账号，运行中只复制 SQLite 主文件可能遗漏 WAL。

恢复时先停止服务，保留故障目录副本，将完整备份恢复到独立目录，设置正确文件权限，再指向该目录启动。用原账号登录并核对材料、任务、问题状态及导出。不要在未确认备份可恢复前覆盖或删除唯一数据。

认证 schema 2 会保留旧账号 UUID 和工作区归属，迁移旧密码验证记录，并使旧会话失效。`AUTH_SCHEMA.json` 声明发行版可读取的认证版本，固定部署 helper 根据 `cashlens_auth_migrations` 检查数据库版本：发布前拒绝降级；发布失败后，仅自动回退到兼容当前数据库的版本。首次跨越 schema 2 后，旧版自动回滚被拒绝，服务停止并保留现有状态，需发布兼容修复版。已经接受新密码、因素或账号变更后，不能随意恢复旧数据库，否则这些变更也会丢失。

## 本轮域名迁移

公网入口统一为 `https://prispect.com`，`www.prispect.com` 使用 HTTPS 跳转至主域。服务器必须将 `APP_ORIGIN` 与反向代理域名同步切换，自动部署的公网健康检查也使用主域；不能只改文档或 DNS。DNS、TLS、公开资产和认证需要在该域另行验收，历史旧域成功记录不替代新域结果。

域名变化不需要重建用户或工作区；保留持久目录、认证数据库与持久密钥。浏览器的旧域会话和本地外观偏好不会跨域迁移，用户需在新域重新登录。通行密钥的 RP ID 来自 `APP_ORIGIN` 的主机名，旧域登记的通行密钥不能用于新域，需用其他可用登录方式登录后重新登记。不得通过扩大受信 Origin 或放宽 Cookie 规则来规避域名绑定。

## 页面路径与刷新

应用使用普通路径，例如 `/docs`、`/account` 和 `/tasks/:id`；查询参数继续携带章节、任务条件与登录返回地址。旧 Hash 页面链接在客户端替换为对应路径并保留查询参数。真实文档锚点、下载、外站链接和新标签页仍由浏览器处理。

生产 Express 服务在静态资源与 API 路由之后提供 SPA 回退，因此直接打开或刷新深页可返回页面入口。Caddy 将同源请求交给该服务，不另外把所有请求重写成 HTML。缺失的 API 保持 JSON 错误与原有认证检查。迁移页面路径无需更改 `APP_ORIGIN`、会话密钥或用户数据库。

## 正式运营的交接事项

- 确认正式域名、TLS、部署用户、持久目录、备份频率与保留期限。
- 确认用户材料处理授权、隐私说明、留存/删除政策及公开数据商业许可。
- 邮箱验证、换绑和找回、手机验证码已提供接口与未配置状态。没有配置邮件或短信供应商时返回不可用，不能产生验证成功状态；实际投递需配置供应商后单独验收。
- 若启用可选模型，由运营方配置本项目专用凭据、服务限额与隐私条件；默认规则模式可以独立运行。
- 根据真实用户并发量做容量与恢复测试。当前架构适合单进程早期服务，不能宣称已验证多节点、高可用或行业合规认证。

这些条件是正式运营的交接事项；本机完整账号和核心处理仍须接受新输入并真实可用。
