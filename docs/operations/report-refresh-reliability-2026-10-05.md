# 刷新与报告可靠性 · 2026-10-05

上一轮保护了浏览器缓存，本轮补齐实际页面的响应顺序。独立工作区基于主线 `9694ec5`；没有修改生产数据、金融计算、模型或页面布局。

## 问题与处理

真实浏览器已复现：刷新 POST 的 202 响应被延迟，期间 GET 已返回完成的新资料；迟到的 202 仍携带上一份资料和 loading 状态，页面会退回旧金额。修改前的浏览器断言实际失败，错误为 `Late loading acknowledgement replaced the completed snapshot`。这与模型判断质量无关，是客户端响应顺序问题。

`shared/company-run-snapshot.ts` 统一页面和缓存的比较：先限定同一研究及输入范围，再比较资料 revision、真实取得时间及分析 revision。同一已完成版本不退回 loading；更高版本的刷新、重新分析和取消仍可正常进入。历史无 revision 的记录使用已记录日期，不伪造版本或时间。不会合并两份原件、改写金额或将旧报告绑定新来源。

页面使用 React 函数式更新比较当前已显示记录，而非请求开始时闭包中的旧记录。缓存沿用同一规则，补齐同 revision 但取得时间较旧的响应保护。旧报告仍保留自己的资料与生成日期；有新资料不等于已有新 AI 报告。

资料更新补齐 operation 标识：同步阻止重复开始；必须仍是同一账号、未取消的当前操作才能更新结果、错误和按钮。切换研究时清除旧标识及忙碌状态，旧请求的 finally 不能清除新操作的状态。取消也增加同步的重复请求保护，既有服务端 revision/CAS 不变。

## 验证

- `tests/company-run-snapshot.test.ts`：资料/分析版本、同资料版本的渐进取得时间、完成/失败/取消与新 loading、历史日期、不同输入范围及不改变数据。
- `tests/company-run-cache.test.ts`：同 revision 的旧快照不能覆盖刷新后的金额和日期；原有账号、删除、容量及晚到响应保护继续通过。
- `scripts/browser-qa.mjs`：延迟刷新确认与新 GET 交错；同一轮双击只发出一份刷新；503 保留金额和上次报告的原日期；真实临时账号内创建第二家公司，切换后的旧响应不会污染当前错误或清除当前忙碌状态。第二份记录仅存在于隔离测试目录，结束后删除。

实际结果：`npm run check` 通过，1112 项测试全部通过，无失败或取消；类型、构建、格式、竞品记录和固定版本仓库规范检查通过。企业流程浏览器验收 33 项通过、8 张截图，无页面异常；账号恢复浏览器验收另有 6 项通过、2 张截图。

全部财务来源使用明确标记的合成输入，外部网络被拦截，未调用实际模型。POST 失败与延迟通过浏览器路由模拟，不冒充生产故障或真实 AI 输出。回执与截图在忽略提交的 `output/browser-qa/`，账号恢复结果在其 `reliability/` 子目录。
