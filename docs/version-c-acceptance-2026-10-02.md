## 验收中修复的问题

1. 原件链接按年份及具体季度匹配，年度不匹配半年度，季度不匹配其他季度；摘要、英文和提示公告不能代替完整报告。早期概览和最终补全采用同一匹配逻辑，原件缺失保持空值。
2. 东方财富公告请求恢复 B 原有的来源 Referer 和浏览器 User-Agent。相同 URL 的旧请求实际返回 HTTP 567，新请求返回真实 JSON。修改限于该来源，超时、请求预算、域名限制与主体过滤继续生效；真实管线读取及分页、跨主体反例已验证。
3. 数据覆盖中的公告来源状态统一为中英文文案，避免展示 `available` 等内部状态码。

公告请求头修复后，再通过真实账号 API 刷新茅台、美的、隆基、紫金和中国建筑五家代表企业。东方财富公告来源均为 `available`，分别取得 242、533、520、494、417 条记录并保留响应哈希；期间与原件链接核对通过，已采用材料和问答没有丢失。部分其他来源仍可能达到读取预算，按实际覆盖显示，不以五家结果宣称所有企业或来源始终完整。

## AI 与隐私边界

使用已配置的 `grok-4.7-fast` 完成八次真实外部模型请求：三个企业问答、一次已确认原件报告解释，以及一条原件核查 graph 中的四次规划和解释。三个问答均为 `mode=model`，引用限定在提供的来源内，规则数值底稿逐字保留。财报解释不改变指标、现金桥和规则结论。

问答采用既有真实企业公开快照，报告解释采用既有已确认原件；它们是新模型调用，不冒充新的数据抓取。原件 graph 实际读取官方主体、目录与近期原件，年报 PDF 复用哈希一致缓存。模型选择的三个附注页随后实际读取；验收脚本限定四次模型请求，后续解释达到该测试预算时如实保留原文和限制。

HTTP 503、伪造来源引用的明确网络夹具均回落到完整规则回答；关闭模型没有外部请求。账号资料、付款计划、私人核查记录不进入企业问答模型载荷。引用白名单和数值检查不等于逐句语义认证。

## 浏览器与接口

- 七个企业栏目、A 的四项核查工具、真实原件候选、来源金额与公式抽屉、六篇文档三栏布局和目录跳转通过；1800×1100、1280×720、390×844、844×390、390×390 的深浅色、双语言和助手输入均验证。
- 十家公司本次新记录均重新打开，九份 A 报告和规则问答记录保留，页面没有 JavaScript 异常。银行按照真实限制展示。
- 实际两个独立账号双向读取、问答和行业跨账号请求返回 404；同一页面切换真实会话后清空旧账号答案和草稿，侧边栏只显示当前账号记录。匿名文档页本地帮助没有请求企业私有接口。
- 另以七项独立接口验证检查 CSRF、并发回答原子保存、快照更新期间旧回答拒绝保存、行业失败刷新保留旧时间戳、删除企业期间的回答不能恢复记录。
- 三十条侧边栏记录的滚动布局和个别缺失状态使用明确浏览器夹具；未声称实际查询了三十家企业。

最终 `npm run check` 通过类型检查、**201 项测试**、构建及格式检查。新增三个来源回归针对报告期错配和实际请求头差异；页面验证另行记录，不用测试数量代替实际功能通过。

## 范围与发布

公告读取有页数、数量和时间预算，部分覆盖仍按部分覆盖显示；工商和司法保留官方人工入口，不能把未取得记录解释为没有风险。本次样本不是全部行业、扫描件或生产容量的认证。现金桥闭合只表明提取金额的算术关系，不证明企业安全。

验收脚本、修复前后快照、独立原表核对、截图和会话分别保存在忽略提交的 `work/verification/version-c-release/`。会话、凭据和完整原件不提交。发布通过现有 main CI 与自动 Deploy；线上结果需以同一提交的 Actions 记录、严格 HTTPS、实际功能和提供的构建资产单独核对。
